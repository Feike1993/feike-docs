# 带鉴权的 SSE 客户端

对应工业前端 `frontend/src/industrial/lib/sseClient.ts`。服务端的 run、seq 与 Redis 回放见[生产 SSE 与断线续传](./sse-resume)；本页解释浏览器怎样**带 JWT 消费该契约，而不是把断流悄悄当成成功**。

## 流程步骤

1. **fetch 建流，而非 EventSource**  
   请求加 `Authorization: Bearer <JWT>` 与 `Accept: text/event-stream`。续传请求另加 `Last-Event-ID`；这两个头是选择 fetch 的直接原因。

2. **增量解码与分帧**  
   `TextDecoder` 把字节块追加到 buffer，只消费完整空行分隔的帧，尾部半帧保留给下一块。每帧抽取 `id`、`event` 与多行 `data`，不能假设一次网络 read 恰好等于一个事件。

3. **按事件类型推进本地状态**  
   `meta` 取得 `runId`，正常事件推进单调 `lastSeq`；`done` 是唯一正常完成标记；`error` 转为 `StreamServerError`，保留 code、message 与 runId 给 UI。

4. **断流不是 done**  
   读取结束但没有终态，且拿到了 `runId` 时才尝试恢复。次数用 `resumesLeft` 限制；没有 runId、次数耗尽或取消时抛 `StreamAbortedError`，不让页面把半句回答记作完成。

5. **坏帧可观测但不拖死整流**  
   未知事件、非法 JSON 或非法 id 交给 `onMalformed`。这使 UI 能记录协议异常，同时避免一个非关键坏帧直接吞掉后续 `done`。

## 应用场景

- 工业页以 JWT 调用 Chat / Agent 流，并在反向代理切换实例后继续同一 run。
- 页面要区分“用户取消”“服务端显式 error”和“网络意外断开”。
- 前端测试要稳定构造半帧、坏 JSON 和 error 事件，而非依赖真实模型流。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| fetch + ReadableStream | 可带自定义头；需自己实现 SSE 解析 |
| done 才成功 | 不吞半截回答；断流需要重试或明确失败 UI |
| 有界续传 | 防无限重试；极短网络抖动之外仍需用户重开 |
| 不认识的 event 仅报告 | 保留前向兼容；需要监控 malformed 数量 |

## 刻意不做

- 不把 JWT 放到 URL query，避免日志与历史记录泄露  
- 不无限重连或把过期 run 当作新对话  
- 不让客户端自行补造 seq 或 done 事件
