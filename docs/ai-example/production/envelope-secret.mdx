# 信封加密与 KEK 轮换

对应生产路径 `com.feike.ai.production.secret`。教学样例继续读 `.env`；工业链路的 LLM Key 和 JWT HMAC 以信封密文进 Postgres，主密钥只留在进程环境里。

## 流程步骤

1. **解析 KEK**  
   `PRODUCTION_KEK` 必须是 Base64 的 32 字节。解析失败时 `SecretResolver.available()` 为 false：`/api/v1` 503，教学样例不受影响。

2. **保护边界**  
   这保护的是备份和 `SELECT *`，**不**保护已经拿到 KEK 的应用进程。因此 KEK 与密文必须分开放，不能把主密钥写进 `prod_secret`。

3. **首次灌入**  
   `SecretBootstrap` 把环境里的 LLM Key 和随机 JWT HMAC 加密写入一次。表里已经有行就不再用 env 覆盖——否则每次重启都会把库内已轮换的密钥打回旧值。失败只打日志，不拖垮启动。

4. **轮换窗口**  
   同时配置 `PRODUCTION_KEK` 与 `PRODUCTION_KEK_PREVIOUS` 时，当前钥匙解不开再试上一把。ADMIN `POST /api/v1/secrets/rotate` 按当前 kek-id 重加密全部行；确认登录仍通后再去掉 previous。

## 应用场景

- 演示「密钥进库必须信封」，而不是把 `.env` 直接拷进业务项目。
- 本机轮换 HMAC / Provider Key，验证重启不会覆盖。
- 工业 JWT 的 HMAC 必须与两台 Java 共享同一信封。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| 密文进 PG、KEK 进环境 | 备份安全；KEK 管理仍是运维问题 |
| 有行不覆盖 | 轮换不被重启打回；换 Key 必须走 rotate 或手工 SQL |
| 缺 KEK → 503 | 教学仍可启动；工业面不可用是显式的 |
| 不做 Vault / 云 KMS | 演示信封语义足够；定时自动轮换本仓不做 |

## 刻意不做

- 不把 PRODUCTION_KEK 写入数据库  
- 不做 HashiCorp Vault / 云 KMS  
- 不做定时自动轮换

JWT 如何用信封里的 HMAC：见 [JWT 与显式 Principal](./jwt-principal)。失败取向总表：见 [Redis 失败取向](./redis-degrade)。
