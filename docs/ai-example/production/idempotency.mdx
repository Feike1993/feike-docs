# HTTP 幂等键

对应生产路径 `com.feike.ai.production.ratelimit.IdempotencyManager`。网络超时后重发 `POST /chat` 或 `POST /agent`，最危险的结果不是“多拿一次 200”，而是**同一轮模型调用、会话写入或工具轨迹执行两次**。

  left="客户端不知道超时前服务端是否已经成功。只按 Idempotency-Key 缓存又会让同一个 key 携带另一份请求体时错误复用旧响应；若 key 不带租户作用域，两个租户还能互相命中。"

/>

## 流程步骤

1. **只给有完成响应的 POST 使用**  
   `POST /chat` 与 `POST /agent` 接受可选 `Idempotency-Key`。GET SSE 不走这套机制：流的恢复标识是 `runId + Last-Event-ID`，见[生产 SSE 与断线续传](./sse-resume)。

2. **先稳定序列化，再计算摘要**  
   Controller 用 JSON Mapper 将请求体序列化，`sha256` 后传给 `begin`。不要用对象内存地址或仅比较 key；相同 key 与不同 body 必须可区分。

3. **Redis 中原子占位或读缓存**  
   首次请求写入处理中状态；相同 hash 的后续请求读取已缓存响应；相同 key、不同 hash 抛业务冲突。key 的作用域包含 tenant，不能只按用户可见字符串存取。

4. **只在业务成功后 complete**  
   Chat / Agent 返回终答后，才把 JSON 响应写入该 key。异常不能伪装成可重放成功响应；客户端应按[错误契约](./error-contract)决定是否换 key、等待或重试。

5. **明确可用性取向**  
   Redis 通信失败时记录 warning 并放行，不让“防重复执行”变成问答可用性的硬依赖。这意味着 Redis 故障窗口内可能重复执行，必须与业务副作用等级一起评估。

## 应用场景

- 移动网络或网关重试提交同一次非流式问答。
- 需要阻止浏览器双击把同一 Agent 请求执行两遍。
- 想把“相同请求的安全重试”和“不同请求误用同一 key”分成可观测的结果。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| key 加 tenant | 隔离正确；跨租户不能共享去重 |
| key 再加 body hash | 防误复用；客户端需在重试时保持请求体一致 |
| 缓存成功 JSON | 重试体验稳定；不缓存失败减少错误状态黏连 |
| Redis 挂了放行 | 主链路可用；极端窗口可能重复执行 |

## 刻意不做

- 不用 Idempotency-Key 代替 SSE 的 run 恢复协议  
- 不保证 Redis 故障期间的 exactly-once 语义  
- 不将没有副作用的 GET 也接入响应缓存
