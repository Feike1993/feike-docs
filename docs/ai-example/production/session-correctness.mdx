# 会话原子轮次与 Redis 软锁

对应生产路径 `com.feike.ai.production.session` 与 `lock`。教学版 JDBC 会话能讲清「消息进库」，但并发下一轮会对不齐。工业链路把**正确性**放在数据库约束上，把 Redis 锁只当成体验优化。

## 双实例互斥

真 Chat 会先过输入护栏才占锁，默认套件打不到 `session_busy`。所以用 `lock-probe` 占 Redis、不打 LLM。解锁必须 Lua 比对 token：持有者若超时，锁可能已被别人拿走，裸 DEL 会删掉别人的锁。

## 流程步骤

1. **整轮原子**  
   user 与 assistant 同一事务。取消或报错不落库：宁可丢一轮，也不让孤儿 user 进入下一轮 prompt。

2. **序号**  
   `INSERT … SELECT COALESCE(MAX(seq), -1) + 1` 消掉「先读再写」窗口。两个事务仍可能读到同一 MAX，此时 `(session_id, seq)` 让后提交者失败，DAO 在事务外重取一次号。

3. **为何不用 @Transactional 重试**  
   主键冲突会把当前事务标成 rollback-only，在里面重试只会连环失败；自调用还不走代理。`TransactionTemplate` 把「一次尝试 = 一个事务」写成显式循环。

4. **幂等**  
   先按 `turnId` 查重，覆盖本类重试和客户端重复提交。库上还有 `uk_prod_chat_message_turn_role`。生产 DAO **没有** `replace()`，只追加。

5. **软锁**  
   `SET key token NX PX ttl`；释放走 CAS。TTL 必须长于一次对话墙钟上限。Redis 挂了**放行**——为锁把整条问答停掉不划算。

## 应用场景

- 多实例下同一 `sessionId` 不能叠两轮流式生成。
- 要把「体验互斥」和「数据正确」拆开讲清楚。
- 对照教学 `JdbcChatSessionDAOImpl` 看并发补丁落在哪。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| 正确性在 PK | 锁可以 fail-open；并发下多一次冲突重试 |
| 只有 done 才写 | 取消干净；用户看不到的半轮不会污染 prompt |
| Lua CAS 解锁 | 比裸 DEL 多一次脚本；避免误删他人锁 |
| 锁 TTL ≈ 流超时 | 进程被 kill 能恢复；过短会误伤慢生成 |

## 刻意不做

- 不把 Redis 锁当成唯一正确性来源  
- 不在教学 DAO 上「修到能上生产」——生产是另一套语义  
- 不在本页抄 Compose 启动命令（见 [双实例 HA](./industrial-ha)）

SSE 为何 Redis 挂了反而要 503：见 [生产 SSE 与断线续传](./sse-resume)。
