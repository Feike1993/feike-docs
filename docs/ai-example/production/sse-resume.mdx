# 生产 SSE 与断线续传

对应生产路径 `com.feike.ai.production.sse`。教学 [逐步 SSE](../principles/observability/agent-tool-sse) 证明「能把 tool 进度推出来」；工业链路还要证明：**断流不等于失败**，换一台实例也能回放。

## run 生命周期

事件顺序固定为 `meta → sources → delta* → usage → done`。任何一步异常收敛成单条 `error`。写出失败（客户端已断开）不再向上抛：业务可以继续算完，事件仍进日志，重连后补齐。

## 跨实例续传

为何用 Stream 而不是 List：entry id 可以显式指定为 `1-<seq>`，「回放 seq 之后」直接 XRANGE，不必把整条流拉回 JVM。状态要单独存一份：run 被取消时可能一条事件都没写出去，只有独立状态能表达「存在过、但没有 done」。

## 流程步骤

1. **契约写在 Writer 里**  
   不让 Chat / Agent 自己 `emitter.send`。三条流（问答、Agent、探针）超时与续传行为才能一致。

2. **看门狗而不是容器超时**  
   `SseEmitter` 的 timeout 会直接结束响应。看门狗先发明确 `error`，emitter 超时设成看门狗加一段余量，只作兜底。

3. **只有 done 才落会话**  
   取消和报错都不写历史。落库失败不改已经流到屏幕上的结论，改为 `persisted:false` 加 error 日志，前端提示「本轮未计入历史」。

4. **续传校验租户**  
   `Last-Event-ID` 回放到另一台实例时按创建者租户校验；跨租户 / 过期窗口给 `run_not_found` 或 `run_gone`，不暴露别人的 run。

5. **fail-closed**  
   断线续传是对外承诺。Redis 不可用抛 503（`event_log_unavailable`），比悄悄退化成「不可恢复」更容易查。

## 应用场景

- 浏览器刷新或反向代理切到另一实例后，要续上同一轮 token 流。
- 需要把 Chat 与 Agent 的超时、续传做成同一套执行器。
- 对照教学逐步 SSE：教学没有日志、没有跨实例。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| Stream + 显式 id | XRANGE 便宜；seq 必须由应用保证单调 |
| 状态与事件分开 | 零事件的取消可表达；多写一个 Hash |
| 看门狗先于 emitter | 用户看得到原因；实现比设一个 timeout 重 |
| Redis 挂了 503 | 不假装能续传；工业流式可用性绑在 Redis 上 |

## 刻意不做

- 不把教学 `/agent/react/stream` 改成这套契约  
- 不做无限期事件存储  
- 不在 Redis 故障时退回「只推一次、不能重连」还当成功

验证双实例回放的脚本在源码仓 `docs/industrial-ha.md`；原理见 [双实例 HA](./industrial-ha)。失败取向总表：[Redis 失败取向](./redis-degrade)。
