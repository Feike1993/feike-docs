# 三种记忆平面

对应 sample **07 / 11–12 / 25**。会话短窗、跨会话用户事实、知识库文档是三类不同数据——先管好窗口，再把长期事实与 RAG 语料分源。

## 流程步骤

### 会话窗口

1. **会话存在应用侧**  
   `ChatSessionStore`：jdbc 写 `chat_session_message`；memory 为 `ConcurrentHashMap`。

2. **先预算，再调用**  
   按 `maxMessages` / `tokenBudget` 选出送入模型的子集，再追加本轮 user。

3. **响应带回可观测字段**  
   `rawMessageCount` / `sentMessageCount` / `approxTokens` / `droppedCount` / `summary`。

### 长期记忆（与 RAG 边界）

4. **同一 vector_store，不同 corpus**  
   用 metadata 过滤 `userId` + `corpus`，不必新建物理表（如 `long-term-memory` vs `ai-example-demo`）。

5. **写入是显式的**  
   本样例不自动从对话抽取事实；生产可另加抽取 Agent。

## 应用场景

- 多轮客服、辅导类会话；需要限制单次请求上下文成本的产品。
- 记住用户昵称、偏好、项目背景；个人助理中「长期画像」与「文档问答」并存。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| 三分平面 | 引用与治理清晰；编排层稍复杂 |
| 记忆召回进 chat | 像「用户事实」而非文档 citation |
| 会话可持久化 | Jdbc 会话对照内存，便于多实例 |

## 刻意不做

- 不把记忆 facts 标成 RAG `sourceId`  
- 不上统一「万能记忆中台」产品形态
