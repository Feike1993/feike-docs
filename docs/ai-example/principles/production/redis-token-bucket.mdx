# Redis 令牌桶

对应生产路径 `com.feike.ai.production.ratelimit`。用 Redis Hash + 单次 Lua 在多实例下原子完成「补令牌 + 扣 1」。

下图是帮助理解算法的主图：读状态、补令牌、判断、写回都在同一脚本里。被拒请求也会写回 `ts`，才能算出准确的等待时间。

桶不按请求记账。默认 `capacity=30`、`window=60s`，每毫秒补充量：

```text
refillPerMs = capacity / window.toMillis()
tokens      = min(capacity, tokens + elapsed * refillPerMs)
```

新 key 以满容量开始。`elapsed = now - ts`，若时钟回拨则按 0，避免错误地扣掉已有令牌。TTL 设为两个窗口：闲置桶自动回收，同时保留一个窗口内的状态，保证补充计算连续。

## 流程步骤

1. **确定 key 与容量**  
   Chat 用 `prod:rl:{tenantId}:{subject}`，走默认容量；登录用 `prod:rl:login:{ip}`，走更严的 `loginCapacity`。`capacity` 参数为 null 或小于 1 时回退配置值。

2. **把结算参数交给 Lua**  
   Java 只算 `refillPerMs`、`now`（`System.currentTimeMillis`）和 `ttl = 2 * window`，然后一次 `EVAL`。不要拆成先读再写。

3. **脚本内补令牌并决定是否扣 1**  
   读 `tokens`/`ts`；新桶满容；按流逝时间补到不超过容量；余额 ≥ 1 则减 1 放行，否则 `retry = ceil((1 - tokens) / refill)`。

4. **放行或抛 429**  
   返回 `{allowed, floor(tokens), retryMs}`。拒绝时变成 `RateLimitExceededException`，Web 层写 `Retry-After` 与 `X-RateLimit-Remaining`。

5. **Redis 挂了降级放行**  
   通信或脚本结果异常打 warn 并返回满容量作为展示值。`RateLimitExceededException` 必须原样抛出，不能被外层 `RuntimeException` 当成 Redis 故障吞掉。

## 应用场景

- 生产问答按租户+用户限流，避免打满模型配额。
- 登录按 IP 用更小容量，抑制撞库。
- 需要跨实例共享、且能给出 `Retry-After` 的 HTTP 限流。

## 设计取舍

| 选择 | 取舍 |
| --- | --- |
| Lua 一次结算 | Redis 对单脚本串行，无 GET/SET 竞争窗口；脚本必须自包含 |
| 只存 tokens + ts | 状态小、好回收；无法按请求审计逐条记录 |
| TTL = 两个窗口 | 闲置自动消失，又保留一个窗口的连续性 |
| Redis 挂了放行 | 限流是保护性优化；与会话锁同向，与 SSE 事件日志 fail-closed 相反 |
| 客户端传入 now | 与 JVM 时钟对齐；跨实例偏差需容忍 |

## 刻意不做

- 不按请求逐条存储访问日志  
- 不把限流做成可用性硬依赖（Redis 故障不停问答）  
- 不拆成多次客户端 Redis 命令  

本机用 k6 打穿桶、读终端摘要：见 [Grafana k6](/docs/tech-stack/loadtest/k6)。Lua 正确性仍看 `RedisTokenBucketIT`，不把压测默认套件打进 CI。
