# 画图工具怎么选

画图不是为了让文档好看，而是为了让读者在短时间内回答一个问题：**系统由什么组成、信息怎样流动、边界在哪里、下一步该改哪里。**

AI 编程时，先让模型生成一个草图很容易；难的是选到能被团队持续维护、能和代码一起演进的表达方式。工具不是越强越好，优先选**最轻、但足以讲清楚当前问题**的工具。

## 先按用途选，不要先按工具名选

先回答下面四个问题：

1. **谁读图**：自己梳理思路、开发团队评审，还是跨团队/面向客户沟通？
2. **图要表达什么**：流程、时序、组件关系、部署拓扑，还是开放式方案草图？
3. **是否需要和代码一起维护**：图是否要进入 Git、接受 Code Review、跟随版本发布？
4. **是否需要多人自由编辑**：讨论时是否要拖拽、批注、摆放便签或快速调整布局？

## 工具速览

| 工具 | 最适合 | 不适合 | 维护方式 |
| --- | --- | --- | --- |
| **Mermaid** | 文档内流程、时序、状态、简单架构 | 高密度复杂架构、强自定义排版 | 源码文本进 Git |
| **draw.io / diagrams.net** | 需要精确排版、导出 PNG/SVG、常规架构图 | 高频随代码演进的图 | `.drawio` 文件进 Git，或导出图片 |
| **Excalidraw** | 方案讨论、白板、低保真草图 | 正式架构基线、需要严格布局的图 | 白板文件或截图，讨论后应沉淀 |
| **PlantUML** | UML、时序、部署图，已有 Java/UML 习惯的团队 | 希望零学习成本的读者 | 源码文本进 Git |
| **Structurizr** | 按 C4 模型维护的大型系统架构 | 一次性小项目、只需一张简单图 | 架构模型进 Git |
| **Archify** | 从代码与配置生成、浏览可交互的系统概览 | 手工讲业务流程、无明确源码结构时 | 生成产物随源码更新 |

## 各类场景的推荐

### 1. README、设计文档、接口说明：Mermaid 优先

当图需要和文字紧挨着阅读，且改动频繁时，Mermaid 的成本最低。它适合：

- 请求链路、Agent 工作流、审批流
- 服务调用与数据流
- 时序图、状态机、Git 分支策略
- 组件不多的系统上下文图

使用边界：一张 Mermaid 图的节点超过约 15～20 个、连线交叉明显增多时，不要继续堆节点。应拆成“系统上下文图 + 局部流程图”，或转为更适合精细布局的工具。

### 2. 需要精确布局或交付图片：draw.io

draw.io（diagrams.net）适合需要拖拽排版、对齐、图例、云厂商图标和导出图片的场合，例如：

- 评审中的服务部署拓扑
- 要嵌入 PPT、方案书、邮件的架构图
- 需要展示 VPC、子网、负载均衡、数据库等基础设施关系

建议把 `.drawio` 源文件和导出的 SVG 一起提交：前者便于编辑，后者便于在文档与代码评审中快速查看。不要只保留截图，否则后续修改常常只能重画。

### 3. 讨论与发散：Excalidraw

在需求还不清楚时，手绘风格的 Excalidraw 能降低“这张图已经定稿”的心理暗示，适合：

- 需求澄清、方案评审、事件风暴
- 组件职责还在调整时的草图
- 结对编程或远程会议中的即时说明

它的产物应该是讨论材料，而不是最终技术基线。讨论收敛后，把关键结论改写为 Mermaid、draw.io 或架构模型；否则白板会很快变成无法检索和维护的历史截图。

### 4. UML 与严格文本化图：PlantUML

团队已经使用 UML，或需要较完整的类图、组件图、部署图时，可以选 PlantUML。它和 Mermaid 一样可被版本控制，但图形语法更偏 UML，也更适合复杂关系。

选它之前要确认两件事：团队愿意维护其语法；文档站或 CI 能稳定渲染。若只是画流程和简单时序图，Mermaid 通常更直接。

### 5. 大型系统架构：Structurizr + C4

当系统包含多个领域、服务和外部依赖，核心问题是“不同层级应该给谁看”时，用 Structurizr 维护 C4 模型更合适：

- **System Context**：系统和用户、外部系统的边界
- **Container**：应用、数据存储、消息队列等运行单元
- **Component**：单个应用内部的主要组件
- **Code**：仅在确有必要时才下钻

它解决的不是画得更漂亮，而是让不同粒度的架构图来自同一模型。小项目不要为了 C4 而引入复杂度；一两张 Mermaid 图已经能说清楚时，Structurizr 是过度设计。

### 6. 从代码获得系统全景：Archify

当系统已有较多源码、基础设施配置和服务依赖，人工架构图容易过期时，优先考虑从源代码或配置生成可浏览的架构概览。Archify 更适合回答：

- 仓库里有哪些服务、入口和依赖？
- 模块之间的真实调用或配置关系是什么？
- 新成员应该从哪里开始阅读？

生成图不能替代人工说明：代码能告诉你依赖关系，却不一定能表达业务目标、权限边界和设计取舍。推荐做法是“生成图保真 + 人工图讲意图”：用生成结果做系统底图，再用简化的 Mermaid 或 draw.io 图说明关键路径。

## AI 生成图时的工作方式

让 AI 直接“画一张系统架构图”，通常会得到看似完整、实际存在臆造依赖的结果。更可靠的流程是：

1. **先给事实，不给结论**：服务列表、接口、数据存储、消息主题、部署边界与已知约束。
2. **限定图的层级与读者**：例如“为后端评审输出一张 Container 级 Mermaid 图”，不要只说“画架构图”。
3. **要求输出可审查源码**：优先 Mermaid、PlantUML、Structurizr DSL 或 draw.io XML，而不是只要图片。
4. **逐项核对节点和边**：每条连线都应能对应代码、配置、接口契约或明确的设计决定。
5. **把图纳入变更流程**：新增服务、队列、外部依赖或跨边界调用时，同步更新相关图。

:::danger[不要把 AI 产图当事实]
模型容易补全“常见但不存在”的 Redis、消息队列、鉴权服务或调用关系。图中的每一个组件和箭头都需要人工验证；不确定的内容应明确标记为“拟定”或删除。
:::

## 一套够用的团队约定

不需要一次性统一所有工具，只要约定以下规则即可：

- **文档内默认 Mermaid**：流程、时序、状态和简单架构图优先用文本化图。
- **复杂架构分层而非堆叠**：先系统上下文，再服务/容器，再局部流程；每张图只回答一个问题。
- **可编辑源文件必须入库**：draw.io、Excalidraw 等不只提交导出图片。
- **图与代码同审**：涉及架构边界、接口、存储或部署的变更，PR 同时更新图或说明无需更新的原因。
- **生成图不替代设计记录**：关键取舍仍应写在 ADR、设计文档或代码注释的合适位置。

## 常见误区

| 误区 | 更好的做法 |
| --- | --- |
| 一张图画完全部服务、表、队列和接口 | 按读者和层级拆图，一张图只回答一个核心问题 |
| 为了“专业”直接上复杂建模平台 | 先用 Mermaid 交付；复杂度真正出现时再升级 |
| 只交付 PNG 截图 | 同时提交可编辑源文件或文本化图定义 |
| 把 AI 自动生成图直接放进正式文档 | 把它当草稿，逐条验证组件和依赖 |
| 图只在立项时画一次 | 把图纳入架构变更的评审清单 |

## 最终建议

如果团队还没有统一规范，可以从下面这套组合开始：

- **日常文档与流程**：Mermaid
- **讨论和方案发散**：Excalidraw
- **需要精细排版或对外交付**：draw.io
- **复杂、长期演进的系统架构**：Structurizr / C4
- **已有系统的真实结构盘点**：Archify 等源码/配置驱动工具

先让图服务于沟通，再让工具服务于图。能和代码一起演进、让下一位读者少问十分钟的问题，才是一张值得维护的图。
